기존 [파주길잡이](https://smile7962.github.io/paju-giljabi/)의 루트 화면을 보존하고 `main/v2/`에서 별도로 이용하는 출장ON AI입니다.
Claude가 만든 원본 디자인 시안은 [design/claude-prototype.html](../design/claude-prototype.html)에 보존했습니다.

**코드 원칙:** 빌드 도구·서버·회원가입 없이 HTML / CSS / 순수 JavaScript로 구성합니다.

## 개발 중 PC 화면 실행

1. GitHub의 `main` 브랜치에서 ZIP을 내려받거나 [배포된 출장ON AI](https://smile7962.github.io/paju-giljabi/v2/)를 엽니다.
2. 압축 해제 후 `v2/index.html`을 Chrome 또는 Edge에서 엽니다.
3. 예시 입력 또는 실제 **공개 가능한 테스트 주소**를 입력하고 `방문지 검색 및 경로계산`을 누릅니다.
4. 경로가 계산되면 `출장계획 확정 · QR`을 누릅니다.
5. 로컬 파일 실행 중에는 QR 생성이 제한됩니다. `이 브라우저에서 미리보기`를 누르면 모바일 현장 화면을 PC에서 체험할 수 있습니다.

## 실제 휴대폰 QR 테스트를 위한 배포

**GitHub Pages에는 기존 파주길잡이와 출장ON AI `v2/`가 함께 배포되어 있습니다.** GitHub Pages 최신 배포 작업 성공 여부는 [Actions](https://github.com/smile7962/paju-giljabi/actions)에서 확인합니다.

휴대폰 QR 테스트는 다음 HTTPS 주소에서 시작합니다. 브라우저와 휴대폰의 실제 동작은 별도 실기기 검증이 필요합니다.

`https://smile7962.github.io/paju-giljabi/v2/`

**주의:** GitHub Pages 배포 성공은 QR·모바일 네비게이션·Gemini 실제 호출의 성공을 보증하지 않습니다. 원본 `index.html`은 변경하지 않습니다.

모바일에서는 `mobile.html#trip=...` 링크로 방문정보를 전달합니다. QR에는 방문지명과 좌표가 인코딩되어 있으며 암호화되지 않습니다. **민원인 이름·전화번호·비공개 현장정보를 넣지 마세요.**

## 사진과 이메일 전송

- 촬영/선택한 사진은 현재 선택한 출장지의 확정 계획주소에 연결됩니다. GPS를 이용해 파일명 주소를 만들지 않습니다.
- 예: `t-..._S01_문발동29-29_01.jpg`
- 사진은 모바일 기기의 브라우저 저장소(IndexedDB)에 저장됩니다. 외부 서버로 자동 업로드하지 않습니다.
- `사진 공유`는 기기의 공유 창을 여는 기능입니다. 이메일 전송은 사용자가 직접 완료해야 합니다.
- 사진 여러 장 공유가 불가능하면 사진마다 `파일 저장`을 이용하세요.
- 현장메모를 PC로 가져오려면 `출장기록 복사`로 텍스트를 복사하여 승인된 업무메일 등에 붙여넣으세요.
- 사진 저장소는 사용자가 브라우저 데이터 삭제를 하거나 기기가 저장공간을 회수하면 소실될 수 있습니다. **출장 종료 후 곧바로 허용된 방식으로 사진을 전송**해야 합니다.
- 브라우저/메일 앱에 따라 공유 시 첨부파일 이름이 바뀔 수 있으므로 PC에서 확인해야 합니다.

## v0.3 외부 내비게이션 연동 (2026-10-14)

- PC 출장계획 완료 후 **출장일정 각 방문지**에 카카오맵 길찾기·네이버지도 검색·T맵 휴대폰 QR 버튼을 제공합니다.
- PC에서 T맵 버튼을 누르면 전체 출장 QR에 **선택 방문지 식별자**를 덧붙여, 휴대폰에서 해당 방문지를 열 수 있습니다.
- 모바일에서 카카오맵은 공식 좌표 길찾기 웹 URL을 열고, 네이버지도는 공식 `nmap://navigation` 스킴, T맵은 `tmap://route` 스킴으로 목적지를 전달합니다.
- 사용자의 휴대폰에 앱이 설치되지 않았거나 웹브라우저가 외부 앱 호출을 차단하면 **모바일 화면에 표시되는 '웹 지도 열기'와 '앱 설치' 버튼을 직접 선택**합니다. 웹에서는 앱 실행 성공 여부를 정확히 감지할 수 없으므로 자동 성공 또는 자동 설치를 표시하지 않습니다.
- 네이버지도 **PC 웹은 장소검색 화면**으로 연결합니다. PC 웹에 좌표를 자동 주입하는 공식 문서화된 URL은 확인되지 않았으므로, PC 버튼에 '네이버 검색'이라고 구분했습니다.
- T맵의 **웹 대체 링크는 카카오맵 좌표 길찾기**입니다. T맵 공식 좌표 웹길찾기 규격이 확인되지 않았으므로 이를 T맵 경로인 것처럼 표시하지 않습니다.
- 예전에 계산한 경로의 주소·방문순서가 수정되면 이전 결과의 QR·인쇄·길찾기 버튼이 비활성화됩니다.
- `v2/nav.js`에서 외부 지도 링크를 관리하며, 복잡한 SDK나 추가 비밀키를 사용하지 않습니다.

**검증:** JavaScript 문법, 생성 URL 파라미터, iPhone/Android 스토어 연결 문자열 검증 완료. 실제 외부 앱 실행 및 대체 경로는 사용자 단말에서 확인 필요.

참고 공식 문서:
- 카카오맵 웹 길찾기: https://apis.map.kakao.com/web/guide/
- 네이버지도 앱 URL: https://guide.ncloud-docs.com/docs/ko/application-maps-url-scheme-vpc

## 인쇄 경로 잘림 수정 (2026-10-14)

PC의 `경로표 인쇄` 버튼은 이제 기존 지도 화면을 축소 인쇄하지 않고 **전용 `v2/print.html` A4 미리보기**를 새 탭으로 엽니다.

1. 출장지를 검색하고 **방문지 검색 및 경로계산**을 완료합니다.
2. **경로표 인쇄** 버튼을 누릅니다.
3. 새로 열린 A4 경로표에서 **파란 경로선과 모든 방문지 마커가 한 지도 안에 표시되는지** 확인합니다.
4. 지도 배경이 로딩된 후 **인쇄하기 / PDF 저장**을 누릅니다.

- 인쇄용 Leaflet 지도를 원래 PC 화면과 별개로 생성하고, 인쇄영역 전체 너비에 맞추어 `fitBounds`를 다시 실행합니다.
- 전체 경로선, 방문순서, 왕복 이동거리·시간, 모바일 QR을 한 문서로 표시합니다.
- 방문지가 많으면 방문목록은 여러 페이지로 이어질 수 있지만 **경로 지도 전체는 한 페이지에서 확인**합니다.
- 계산한 경로는 동일 출처의 브라우저 저장소에 인쇄를 위한 임시 데이터로 보관합니다. 1시간 후 출력에 사용하지 않습니다. **민감한 출장지·민원인 정보를 입력하지 마세요.**
- 브라우저에서 직접 Ctrl+P를 누르는 대신 앱의 **경로표 인쇄** 버튼을 사용하세요.

## v0.4 출장복명 기능 (2026-10-14)

1. PC에서 출장계획의 `출장계획 확정 · QR`을 눌러 해당 출장을 저장합니다.
2. 출장지별로 휴대폰에서 현장사진을 촬영하고 **사진 공유**를 이용해 허용된 이메일 등으로 사진 파일을 PC에 전달합니다.
3. 휴대폰의 **출장기록 복사** 내용을 이메일 본문 등으로 PC에 전달합니다.
4. PC에서 `출장복명 작성`을 눌러 `/v2/report.html`을 엽니다. 반드시 출장계획을 생성한 **같은 PC·같은 브라우저 프로필**이어야 합니다.
5. 오른쪽 `모바일 출장기록 가져오기` 입력창에 복사한 내용을 붙여넣고 `출장기록 적용`을 누릅니다.
6. 이메일로 받은 현장사진을 **사진 여러 장 선택**으로 불러옵니다.
7. `출장ID_S01_계획주소_01.jpg` 형식으로 **출장 ID + 방문지 ID + 계획주소**가 모두 일치할 때만 자동 분류됩니다. 다르게 저장된 사진은 수동 분류합니다.
8. 방문지별 현장확인내용·조치사항·사진설명을 수정하면 가운데 A4 문서가 즉시 갱신됩니다.
9. `인쇄 / PDF 저장`을 누르면 문서와 사진대지를 출력합니다.

### 제한사항 및 보안

- **실제 AI 연동 전:** 사용자 입력 사실만 서식에 배치합니다. AI가 사실을 임의 작성하지 않으며 문장 정리 기능은 다음 단계입니다.
- **서식은 시연용 기본 양식입니다.** 파주시 출장복명서 원본 서식(HWPX 등)을 제공받으면 반영합니다.
- 보고서 작성 중 메모는 PC localStorage에, 불러온 사진은 PC IndexedDB에 저장됩니다. 브라우저 데이터를 지우면 소실될 수 있습니다.
- 휴대폰 사진과 PC의 사진 저장소는 자동 동기화되지 않습니다. **이메일 등을 통한 사용자의 파일 전달이 반드시 필요합니다.**
- HEIC/HEIF 사진은 브라우저와 출력 기능의 지원 여부가 다릅니다. PDF에 넣으려면 JPEG 또는 PNG로 변환한 뒤 불러오세요.
- 같은 출장의 사진이더라도 이메일 앱이 파일명을 변경할 수 있습니다. 이 경우 **수동 분류**가 필요합니다.
- 사진을 외부 서버로 자동 업로드하거나 AI에 전달하지 않습니다. 개발/검증은 개인정보·비공개 민원사진을 제외한 모의자료로 진행하세요.
- 사진은 최대 60장, 한 파일당 25MB까지만 처리합니다. 대량 사진일 때 브라우저 저장공간과 인쇄 성능에 주의하세요.
- 여러 건을 관리하는 중앙 서버는 없습니다. 같은 브라우저에서 '가장 최근에 확정한 출장계획'을 기준으로 문서를 엽니다.
- 개인정보·보안 심사 없이 실제 행정업무 자료를 투입해서는 안 됩니다.

## v0.5 장소별 개별 출장결과보고서 (2026-10-15)

**변경 이유:** 여러 출장지를 하나의 보고서에 묶으면 추후 장소명·민원별 문서 검색이 어렵습니다. 이에 **하나의 출장계획에 여러 개의 독립된 결과보고서**를 연결합니다.

- 예: 3곳 출장 → 출장계획 1건 / 결과보고서 3건 / 각 장소 현장사진대지 별도 출력
- 왼쪽에서 출장장소를 선택하면 **중앙 A4 문서에는 해당 출장지만 표시**됩니다.
- 각 방문지는 독립된 출장일시·참석·현장 확인내용·조치사항·문서번호를 저장합니다.
- 출장일자·출장자·출장목적·관련문서·보고일자는 출장계획의 공통 기본정보입니다.
- 오른쪽 현장사진 관리에서는 **선택 장소와 미분류 사진**만 표시합니다.
- 저장 파일명 예: `출장결과보고서_20261015_문산읍임진각로177_S01_abc123.pdf`.
  브라우저 **PDF 인쇄창의 기본 제목**으로 설정하지만 실제 저장파일명은 사용자의 브라우저·OS 설정에 따라 달라질 수 있습니다. 최종 저장 시 확인하세요.
- 사진파일명 자동분류 규칙(출장 ID + 방문지 ID + 계획주소)과 휴대폰 메모 인계는 기존 방식 유지.

### 제공된 「출장결과보고서.hwpx」 양식 반영

문서 기본 제목과 구조를 다음과 같이 변경했습니다.

- 상단: `문서번호`, `보존기간(3년)`, `보고일자`, `결재일자`, `공개여부`, `출장자`, `건축신고3팀장` 결재란
- 본문: **출장결과보고서** / 관련문서·출장목적 / **□ 개요** / `ㅇ 일시`, `ㅇ 장소`, `ㅇ 참석`, `ㅇ 내용`
- 끝: `붙임 현장사진 1부. 끝.`(실제로 사진이 존재할 때) / `파 주 시 장 귀하`

**웹 A4 미리보기**는 제공된 HWPX 항목을 HTML로 재구성한 것으로 원본의 모든 위치를 재현하지 않습니다. **별도의 '원본 HWPX로 저장' 기능**은 사용자가 선택한 원본 XML 서식을 보존하여 출력하며, 원본 파일은 공개 저장소에 올리지 않았습니다.

## v0.6 원본 HWPX 서식 유지 및 온나라 파일 불러오기 준비 (2026-10-15)

**핵심 목표:** 사용자 PC에서 기존 **파주시 출장결과보고서.hwpx**를 선택하고, 선택한 출장장소의 내용만 원본 서식에 채운 HWPX를 내려받아 한글에서 검토한 뒤 온나라에서 파일 불러오기.

1. PC 출장계획을 확정하고 `출장결과보고서` 화면을 엽니다.
2. 좌측에서 **보고할 출장장소 1곳**을 선택합니다.
3. 오른쪽의 **원본 HWPX 서식**에서 사용자가 가진 **출장결과보고서.hwpx**를 선택합니다.
4. 출장자·일시·참석·현장 확인내용·조치사항 등을 작성합니다.
5. 중앙 문서에서 내용을 확인하고 **원본 HWPX로 저장**을 클릭합니다.
6. `출장결과보고서_날짜_장소명_장소ID_출장ID.hwpx` 파일이 내려받아집니다.
7. 내려받은 HWPX를 한글 프로그램으로 열어 표·내용·서식·줄바꿈을 점검하고, 필요하면 한글에서 다시 저장한 후 **온나라에서 파일을 불러오기** 합니다.
8. 다른 출장장소를 선택하면 원본 양식으로 별도의 HWPX를 생성합니다.

### 원본 보존 방식

- HWPX는 원본의 ZIP/XML 패키지입니다. 이 기능은 새 문서 서식을 만드는 것이 아니라 **원본 파일을 복사하여 본문 XML의 텍스트만 교체**합니다.
- `Contents/section0.xml`의 문서번호, 보고일자, 출장자, 제목의 출장목적, 개요(일시·장소·참석·내용)를 수정하며 다른 구성파일과 원본 결재란/표/스타일은 유지합니다.
- 문서 내 결재일자·공개여부 등 입력되지 않은 필드는 임의로 생성하지 않습니다.
- 원본 HWPX 파일은 **웹브라우저 메모리 안에서만 사용**합니다. 서버·GitHub·AI API에 올리지 않으며, 새로고침 후에는 다시 선택해야 합니다.
- 유효한 HWPX MIME/파일구조 및 제공된 출장결과보고서 원본 표 구조를 확인하고 다른 양식이면 출력하지 않습니다.
- `v2/hwpx.js`의 단일 모듈과 JSZip 라이브러리를 사용합니다. 템플릿 저장 기능, 별도 백엔드/로그인 시스템은 추가하지 않았습니다.

### 현재 한계 — 반드시 확인

- **v0.6 당시 한계였던 HWPX 사진 미삽입은 v0.8에서 개선했습니다.** JPG·PNG·WEBP로 분류된 사진은 원본 보고서 뒤에 자동 삽입합니다. 출력 후 한글에서 열리는지 반드시 확인해야 합니다.

## v0.7 — 온나라 기본 글씨 제거 + 현장메모 초안 작성 (2026-10-16)

### 1. 원본 HWPX 상단 빨간 글씨 공란

원본 `출장결과보고서.hwpx`에는 온나라에서 입력해야 하는 값 **`3년`**(보존기간 칸)과 **`건축신고3팀장`**(결재란 상단)이 기본으로 설정되어 있습니다. 이전 버전은 이를 그대로 내보냈으므로 두 텍스트가 나타났습니다.

- HWPX 생성 시 **상단 표의 해당 두 칸의 글자만 비웁니다.**
- 표의 크기·병합·선·글자 속성은 유지하며 `문서번호`, `보존기간`, `출장자` 등의 검은색 항목명도 유지합니다.
- 본문은 출장목적/일시/장소/참석/현장확인내용/실제 조치사항에 한해 입력합니다.
- 기타 온나라 관리 필드는 작성하지 않습니다.
- 예전 HWPX의 프리뷰 썸네일 캐시에는 원래 글씨가 남을 수 있어, **실제 한글 프로그램에서 열어 본문/상단 표를 확인**하세요.

### 2. 즉시 사용할 수 있는 로컬 문장 정리

현장확인내용 또는 실제 조치사항을 입력한 뒤 **현장메모 문장 정리 (로컬)** 버튼을 누릅니다.

- 불필요한 줄 앞 기호·공백을 정리하고 문장 끝 마침표를 보완합니다.
- 원본의 사실관계는 변경하지 않으며 내용이 없는 항목을 추측해서 채우지 않습니다.
- 결과는 **초안 미리보기**에 나타납니다. 사용자 검토·수정 → **확인 후 적용**을 누를 때만 현장내용에 반영합니다.
- 이 기능은 규칙 기반 문자열 정리이며 **생성형 AI가 아닙니다**. 오프라인에서 작동합니다.

### 3. 생성형 AI 초안 — 프록시 연결 시만 사용 가능

UI의 **생성형 AI 초안 요청** 기능은 `v2/worker/ai-draft.js`에 포함된 서버 측 프록시 예제를 별도 배포한 뒤, 승인된 HTTPS **`/draft`** 주소를 지정해야 작동합니다. **현재 저장소/Pages 배포만으로 Gemini API에 연결되지 않습니다.**

- AI 키는 서버 측 `GEMINI_API_KEY` 비밀 환경변수로 관리합니다. 웹앱에 비밀키를 넣지 않습니다.
- 명시적으로 AI 요청 버튼을 누르고 데이터 전송 여부를 확인한 경우에만 `장소·시간·참석·출장목적·현장확인내용·조치사항` 텍스트를 전송합니다.
- 사진·원본 HWPX·다른 출장지 기록은 전송하지 않습니다.
- 모델에는 입력된 사실만 공문서체로 정리하고 새로운 사실·조치결과를 만들지 말도록 지시합니다. **AI 생성문구를 그대로 신뢰하지 말고 담당자가 대조·수정**합니다.
- 입력내용을 수정하거나 출장지를 바꾸면 아직 적용하지 않은 초안은 폐기합니다.
- 프록시 예제는 프로토타입 참고용입니다. **CORS만으로 인증·오남용을 막을 수 없으므로 기관 보안검토, 인증, 접근제한, 사용량 제한 없이 공용 인터넷에 배포하지 마세요.** 서비스 공급자의 데이터 처리·학습·보존 정책도 별도로 확인해야 합니다.
- 실제 민원인·비공개 현장정보는 공개 AI 서비스로 전송하지 마세요. 대회 시연은 **합성데이터만** 사용합니다.

### 4. 이번 변경 파일

`v2/hwpx.js`, `v2/report.html`, `v2/report.js`, `v2/report.css`, `v2/draft.js`, `v2/worker/ai-draft.js`와 이 README입니다. 기존 파주길잡이 `index.html`은 변경하지 않습니다.

## v0.8.1 — HWPX 저장 실패 보완 (2026-10-16)

현장사진이 PC 화면에 표시되지만 **원본 HWPX로 저장** 시 파일이 내려받아지지 않는 문제를 조사해 오류 판별·저장 경로를 보완했습니다.

2. 원본 `출장결과보고서.hwpx`(이전에 작성한 결과보고서가 아닌 **빈 원본**)를 선택합니다.

- Gemini API 키는 서버 환경변수 `GEMINI_API_KEY`에만 저장합니다. 프록시 토큰 `TRIPON_DEMO_TOKEN` 역시 서버 측 비밀변수입니다. 브라우저에는 값을 사용자가 직접 입력하며 저장하지 않습니다.
- 출력은 `purpose/check/action` 3개 문자열만 허용합니다. 출장 날짜·장소·참석자·사진·문서번호·HWPX·다른 출장지 내용은 AI가 수정하지 않습니다.

- **프로그램 배포와 AI Worker 배포는 별도입니다.** GitHub Pages에는 v1.5 UI가 배포되어 있습니다. 승인된 프록시 서버는 별도 설정이 필요하며, v1.5의 Gemini **직접 연결**은 Worker 없이 합성 시연만 가능하되 실제 200 응답과 브라우저 CORS는 아직 실기기 확인 전입니다.
- **설치·설정·검증:** [v2/worker/SETUP.md](worker/SETUP.md). 실무자료의 외부 전송은 기관 보안 승인 전까지 금지합니다.

### AI 기능 테스트

1. 기존 HWPX와 사진 저장 기능이 정상인지 확인합니다.
2. PC 출장결과보고 화면 오른쪽에서 **현장메모 문장 정리(로컬)**을 실행해 외부 연결 없이 작동하는지 확인합니다.
3. 별도 Worker 설치 후 URL·접근 토큰을 입력하고 **합성자료로 AI 연결 테스트**를 클릭합니다.

5. 적용 뒤 해당 출장지 HWPX를 저장합니다. **AI는 서식을 수정하거나 온나라 결재정보를 생성하지 않습니다.**

## v1.0 — 시간약속·우선방문을 고려한 출장일정 계산 (2026-10-17)

출장계획 화면에서 **방문 우선순위·시간제약 사용**을 선택하면 기존 경로계산과 별도로 다음 조건을 적용합니다.

- **출발 예정시각:** 24시간 기준 HH:MM. 기본 09:00
- **현장 체류시간:** 모든 방문지에 공통으로 적용하는 0~180분. 기본 20분
- **가장 먼저 방문할 곳:** 한 곳을 1순위로 고정 (선택사항)
- **방문약속:** 한 곳을 지정해 업무를 약속시간에 시작. 일찍 도착하면 대기하고 늦으면 해당 순서를 불가로 판정 (선택사항)
- **최종 복귀시각:** 지정시간을 넘는 계획을 불가로 판정 (선택사항)
- **입력한 방문순서 유지:** 체크하면 순서 최적화 없이 입력순서를 그대로 검증. 지정한 1순위가 입력 첫 방문지와 충돌하면 오류

### 계산 방법

1. 기존 카카오 장소/주소 검색·OSM 폴백으로 좌표 확정
2. 공개 OSRM `/table/v1/driving`으로 **방문지 간 도로 이동시간 행렬** 조회
3. 최대 15곳까지 결정론적 후보 경로 탐색(beam search). 약속시각, 우선방문, 체류시간, 당일 복귀 상한을 검증
4. 선택된 방문순서로 **기존 `/route/v1/driving`**을 호출해 실제 도로경로 선, 거리, 이동시간 표시
5. 출장일정 오른쪽 목록 및 A4 경로표에 **도착·업무시작·업무종료·대기·복귀 예상시각** 표시
6. 출장계획 확정 후 QR 모바일 인계와 출장장소별 HWPX 기능은 기존대로 사용

**주의 및 제한**

- 이 방식은 **생성형 AI가 아니라 시간제약을 고려하는 경로계산 알고리즘**입니다. 방문순서 최적화는 휴리스틱이며 전역 최적을 보증하지 않습니다.
- 약속은 **한 방문지에 정해진 한 시각만** 지정할 수 있습니다. 여러 방문약속·방문지별 서로 다른 체류시간·날짜 넘김은 다음 단계입니다.
- `HH:MM` 시각을 기준으로 **당일만** 계획하며 실시간 교통·돌발 정체·주차시간·휴식·현장지연은 반영하지 않습니다.
- 조건에 맞는 경로를 탐색하지 못하면 **성공한 척 표시하거나 조건을 임의로 무시하지 않고** 오류를 표시합니다. 탐색 방식의 특성상 실제 가능 경로가 있어도 놓칠 수 있으므로 출발시간/복귀시간/약속조건을 변경해 재계산해 보세요.
- **OSRM Table 예상 도착시간은 도로망 추정치**입니다. 최종 지도·거리/이동시간은 OSRM Route 조회값이므로 소수의 차이가 있을 수 있습니다.
- **QR은 방문지 순서와 좌표를 전달**하며 약속시간·체류시간을 모바일에서 자동 알림으로 관리하는 기능은 아직 없습니다. 이 내용은 PC 일정표와 A4 경로표에서 확인하세요.
- OSRM·주소검색은 외부 공용 서비스입니다. 비공개 출장 위치·민원인 개인정보를 입력해서는 안 됩니다.
- 시간제약 체크박스가 꺼져 있으면 **기존 OSRM 일반 경로 최적화**가 변경 없이 작동합니다.

### 검증 시나리오

- 우선방문지 지정: 입력 2번 방문지를 실제 방문 첫 순서로 배치
- 약속시간 10:00: 해당 장소가 늦지 않게 도착, 일찍 도착 시 대기
- 현장 체류 20분씩: 3곳 체류 총 60분 산입
- 복귀제한 10:30: 조건이 충돌하는 시뮬레이션에서 계산 중지 및 경고
- 방문지 15곳: 중복 없이 모든 장소를 방문순서에 배치
- 기존 일반 계산: 체크 해제 시 `/trip/v1/driving` 등 종전 계산 방식 유지

## v1.1 — 출장지별 체류시간과 여러 방문약속 (2026-10-18)

v1.0에서 모든 출장지에 동일하게 적용하던 체류시간과 하나의 방문약속 제한을 확장했습니다. **출장지마다 서로 다른 현장 체류시간과 약속 시작시각을 정하고, 이를 동시에 지키는 순서를 탐색**합니다.

### 입력 방식

1. PC 출장계획 화면에 출장지 주소를 한 줄에 한 곳씩 적고 **방문 우선순위·시간제약 사용**을 켭니다.
2. 출발시각과 **기본 체류시간**(기본 20분)을 입력합니다.
3. 아래에 표시된 **출장지별 체류시간·방문약속** 목록에서 각 출장지의 시간을 정합니다.
   - 체류시간 칸을 **비워 두면 기본 체류시간**을 적용합니다. 별도 값을 넣으면 해당 출장지에만 반영됩니다.
   - 약속시간을 비워 두면 자유 방문이 가능하고, 시간을 입력하면 **그 시간까지 도착해 해당 시간에 현장업무를 시작**하도록 계획합니다.
   - **여러 출장지에 각각 약속시간**을 입력할 수 있습니다.
4. 필요한 경우 가장 먼저 방문할 곳과 최종 복귀시간을 정합니다.
5. 계산하면 시간제약을 만족하는 방문순서가 지도·QR에 반영되고, PC·A4 출장일정에는 도착·약속·업무시작/종료·대기·복귀시각이 표시됩니다.

### 안전한 동작

- **장소명 연결 보존:** 주소 목록의 순서를 변경해도 방문지별 설정은 동일 주소명에 연결해 보존합니다. 기존 주소를 다른 주소로 바꾸면 새 주소의 설정은 공란으로 시작합니다. 입력이 중복된 장소는 기존과 같이 경로계산을 거부합니다.
- **시간 충돌 검사:** 두 약속시간에 모두 도달할 수 없는 경로는 가능한 것처럼 임의 수정하지 않고 오류를 표시합니다.
- **개별 체류시간 검증:** 출장지별 0~180분, 기본 0~180분, 약속시각 HH:MM, 당일 계획만 지원합니다.
- **계산:** 기존 OSRM 도로 이동시간 행렬을 사용하며 여러 약속의 시간 한계를 탐색 중에 검사합니다. 최대 15개 방문지, 휴리스틱 후보 경로 100개 제한으로 **가능한 경로의 존재나 전역 최적을 보장하지 않습니다.**
- **일반경로 후방 호환:** 시간제약을 해제하면 기존 v1.0 OSRM 경로계산 로직 그대로 사용합니다.
- **HWPX·사진대지·온나라 결재란:** 변경하지 않습니다. QR에는 기존대로 장소 순서·좌표만 전달하며 개별 약속시간을 휴대폰 앱에 저장하거나 알림을 보내지는 않습니다.
- **보안:** 지도검색과 OSRM은 외부 공용 서비스입니다. 개인정보나 공개할 수 없는 출장지 정보를 넣지 마세요.

### 검증 결과 (합성 좌표·도로시간 자료)

- 출발 09:00, 우선방문 2번, 3번 약속 10:00, 1번 약속 11:00, 출장지별 체류시간 35·10·25분 → **방문순서 2→3→1, 약속시각 준수, 체류 총 70분, 대기 총 35분, 11:45 복귀**
- 같은 두 약속을 도로상 달성할 수 없도록 변경 → 계산 불가 오류
- 방문지 A·B·C를 C·A·B 순서로 재배열해도 장소별 입력값과 우선방문 지정이 각 장소를 따라가는지 UI 통합검사 통과
- 기존 v1.0 시나리오 포함 총 **11개 경로 엔진 회귀검사** 통과, 지도·일정·QR 순서 일치 모의 확인

### 사용자가 추가 검증할 사항

공개·시연 가능한 주소 3곳을 지정해 약속시각 2개와 서로 다른 체류시간을 설정하고 실제 OSRM 결과와 A4 경로표를 확인하세요. **실제 교통소요시간, 주차·도보·비상상황은 반영되지 않습니다.**

## v1.2 — PC 확정 출장시간표를 QR로 휴대폰에 인계 (2026-10-19)

**목표:** 기존 PC 출장계획 → 모바일 현장출장 단계에서 방문지 순서·위치뿐 아니라 **출발·예상 복귀·도착예정·현장업무 시작/종료·약속 여부**를 함께 전달합니다. 현장사진·출장메모는 QR에 포함하지 않습니다.

### 사용 방법

1. PC에서 3~15곳 공개 시연용 장소를 입력합니다. **방문 우선순위·시간제약 사용**을 선택하고 각 출장지의 체류시간·약속시각을 지정합니다.
2. **방문지 검색 및 경로계산**을 한 뒤 **출장계획 확정·QR**을 누릅니다.
3. 휴대폰에서 QR 스캔 → 모바일 출장화면의 **확정된 출장 예정시간표**에서 현재 출장지 시간 확인.
4. **전체 방문지 시간표 보기**를 펼쳐 각 장소의 예상도착·약속시각·현장업무 종료시각을 확인할 수 있습니다.
5. 방문지를 전환해도 해당 출장지의 예정시간이 표시됩니다. 기존 카카오·네이버·T맵 길찾기, 현장도착·사진·메모·메일 공유는 그대로 작동합니다.
6. QR를 인쇄한 A4 경로표에도 동일한 정보를 넣습니다. 단, 실제 경로표의 문자로 된 예정시각은 원래대로 표시합니다.

### 간결한 서버 없는 QR 데이터 구조

- 기존 포맷 `[1, tripId, origin, visits]` 그대로 지원. 시간 없는 기존 QR은 모바일에서 **시간표 패널을 자동 숨김**.
- 시간제약 경로일 때만 다섯 번째 필드 `[출발(분), 복귀(분), 압축된 방문시간문자열]` 추가.
- 방문시간 1건은 `예상 도착 3자리 base36 + 업무 시작 3자리 + 업무 종료 3자리 + 약속 여부 1자리` **10자**로 압축합니다. 분 단위 값은 0~1439의 정수입니다.
- QR 파싱 시 데이터 길이·약속여부·시간순서·유효 범위를 검사하고 변조/손상 값은 거부합니다.
- PC/인쇄용 QR URL 상한 1,900자. 용량 초과 시 계획 **시간표를 제외한 장소 정보만 인계**하며, PC에 이를 명확하게 표시합니다. 방문지명 단축·출장계획 분할 권장. 15곳도 통과하는 대표 주소 조합을 검증했지만, 매우 긴 주소는 용량을 넘을 수 있습니다.
- URL `#` 뒤에 인코딩된 데이터로 전달합니다. 별도 사진서버·중앙 데이터베이스·계정 없이 작동합니다. **개인정보/비공개 출장주소를 외부에 공유하는 데 사용하면 안 됩니다.**

## v1.3 — 모바일 현장사진·메모를 PC 출장복명으로 안전하게 인계 (2026-10-19)

모바일 현장출장에서 기록한 자료를 실제 출장 장소별 PC 결과보고서와 연결하는 구간을 검증·보완했습니다. **모바일에서 이메일을 자동 전송하지 않으며, 사용자가 허용된 전송방법을 직접 선택합니다.**

### 사용방법: 휴대폰 → PC

1. PC 출장계획을 확정하고 QR을 휴대폰으로 읽은 다음, 1~3곳의 **합성·공개 시연용 출장지**에서 현장메모와 시험사진을 기록합니다.
2. 모바일 **사진·출장기록 공유** 버튼을 누릅니다. 휴대폰이 사진+TXT 동시 첨부를 지원하면 사진과 `출장ID_출장기록.txt`를 함께 공유합니다. 가능하지 않으면 사진만 공유하거나 별도 **출장기록 TXT 저장** 버튼을 사용합니다.
3. 휴대폰의 파일 공유 시트에서 허용된 이메일 앱을 선택하고 첨부파일·실제 전송 결과를 직접 확인합니다. 파일명은 지정된 출장ID·방문지ID·확정 계획주소·사진번호를 사용하며 **GPS 역주소를 사용하지 않습니다.**
4. PC 같은 브라우저의 출장복명 화면에서 **출장기록 TXT 불러오기**를 클릭해 전달받은 `.txt` 파일을 선택합니다. **출장ID 검증 후 화면 텍스트 영역에만 불러옵니다.**
5. 내용을 검토하고 **출장기록 적용**을 눌러 방문지별 현장 확인내용 초안에 반영합니다. **기존 작성 내용은 덮어쓰지 않고**, 주소·출장ID 불일치 시 가져오지 않습니다. 복사해 붙여넣는 기존 방식도 유지합니다.
6. PC에서 **사진 여러 장 선택**으로 첨부받은 사진을 불러옵니다. 파일명이 `출장ID_S01_계획주소_01.jpg` 등과 일치하면 자동으로 방문지에 분류합니다.
7. 출장지별 확인내용·조치사항·사진설명을 검토하고, **원본 HWPX로 저장**을 눌러 해당 출장지의 사진만 들어간 HWPX 보고서를 생성합니다.

### 내부 변경사항 및 오류 예방

- `v2/handoff.js`에 **모바일과 PC의 동일한 계획주소 파일명 규칙**, 사진 방문지 연결검사, 텍스트 출장기록 만들기/읽기를 한곳에 모았습니다.
- 파일명은 기존과 동일하게 공백·금지문자 제거 후 최대 48글자로 처리합니다. 실제 운영에서 서로 다른 주소가 같은 단축파일명이 되지 않도록 출장ID와 방문지ID도 함께 검증합니다.
- `출장기록 TXT`는 Windows 한글 텍스트 앱에서 읽기 쉽도록 UTF-8 BOM으로 생성합니다. PC에서는 BOM과 Windows 줄바꿈을 제거하고 출장ID·방문지 주소를 대조합니다.
- TXT 파일은 200KB 이하만 선택 가능하며 텍스트 본문은 10만 글자 이하로 검증합니다. **파일을 선택했다는 이유만으로 자동 보고서 저장이나 AI 전송은 일어나지 않습니다.**
- 이미 작성한 현장 확인내용은 메모를 적용해도 보호합니다. 새로 반영된 문안은 사용자 검토 후 AI 초안 작성 또는 HWPX 문서로 사용할 수 있습니다.
- 현장사진은 이메일 앱에 따라 이름이 변경될 수 있습니다. 자동분류에 실패하면 **PC에서 해당 출장지를 수동 선택**해야 합니다. 사진별 설명은 사용자가 입력합니다.
- 같은 방문지의 사진은 파일명 끝의 사진번호를 우선해 순서대로 문서에 넣습니다. HEIC/HEIF 사진은 원본 HWPX 사진첨부 전 JPG로 변환해야 할 수 있습니다.
- 로컬 사진·메모·HWPX는 별도 서버에 업로드하지 않습니다. **실제 업무자료의 외부 공유, 공용 지도/API 입력은 기관의 개인정보·보안승인 범위 내에서만** 진행하세요.

### 검증 및 실기기 확인

- 공통 인계 모듈의 **6개 회귀시험**: 기존 사진 파일명 형식, 서로 다른 출장ID/방문지/주소 차단, 한국어 여러 줄 메모 및 BOM/CRLF, 무내용 메모 생략, 손상·과대 TXT 거부 통과.
- 모바일·PC JS 문법, 공유·TXT 저장·TXT 선택·기존 HWPX/사진 UI 요소 및 스크립트 순서 확인.
- 실제 휴대폰 Web Share에서 `사진 + TXT` 동시 첨부가 가능한지, 이메일 앱이 사진명을 유지하는지, PC에서 받은 파일의 자동분류 결과는 **사용자 실기기 시험 필요**.
- **실기기 점검 기준:** 두 출장지별 사진 한 장 이상과 메모를 저장 → 공유/다운로드 → PC TXT 불러오기 → 작성내용 확인 후 적용 → 사진 2장 분류 → HWPX 열기. 다른 출장 사진이나 미분류 사진은 HWPX에 포함돼서는 안 됩니다.

## v1.4 — 실제 Gemini 연결 전 단계: 프록시 검증·오류 처리 강화 (2026-10-19)

**현장사진·메모 → PC → 장소별 HWPX 실기기 시험 완료** 후, 생성형 AI 초안 생성의 서버 검증을 진행했습니다.

- 기본 생성모델: **Gemini 3.5 Flash-Lite** (`gemini-3.5-flash-lite`). 공식 Gemini 구조화 출력 REST API의 `generationConfig.responseFormat.text` JSON 스키마 방식을 사용합니다.
- AI Worker는 GitHub Pages와 **별도 배포**가 필요합니다. Cloudflare Worker 계정·Gemini API 키·서버 접근 토큰이 없으므로 **아직 실제 모델 응답 연결은 완료되지 않았습니다.** API 비밀키는 절대 채팅·소스·브라우저 파일에 입력하지 않습니다.

- `v2/draft.js`는 현장메모가 허용 길이를 넘을 경우 **잘라 보내지 않고 요청을 차단**합니다. Worker가 반환한 비밀정보가 없는 서버 진단을 사용자에게 표시하며, CORS/서버 응답지연에 대한 오류도 구분합니다.
- **아무리 정상적인 AI 응답이어도 즉시 문서에 반영하지 않습니다.** 기존 담당자 검토 → 수동 편집 → 확인 후 적용 → 원본 HWPX 저장의 순서를 유지합니다.
- `v2/worker/.gitignore`로 `.dev.vars`, `.env`, `.wrangler` 등 비밀·캐시파일을 소스 업로드에서 제외합니다.
- **모의 시험:** Worker 요청 스키마·키 비노출·토큰/출처/추가필드 차단·제공자 오류 등 13개 검사 통과, 브라우저 AI 호출·응답·안전 차단 등 8개 검사 통과. `node --test v2/worker/ai-draft.test.mjs v2/tests/draft-ai.test.mjs` 자동시험용 파일을 등록했습니다.
- 설치 매뉴얼은 `v2/worker/SETUP.md`를 참고하세요. Worker 계정 소유자가 실제 배포하고 합성자료 연결 테스트를 완료해야 **실제 AI 연결 성공**입니다.

**개인정보 주의:** Google 공식 가격표에 따르면 Gemini 무료 사용 티어 자료는 제공자 제품 개선에 활용될 수 있습니다. 이 프로젝트의 무료 Worker는 **공개 가능한 합성 출장자료 시연 전용**입니다. 승인받지 않은 실제 현장자료·민원내용은 전송하지 않습니다.

## v1.5 — Gemini 직접 연결 / 보안 프록시 선택 (2026-10-19)

**Cloudflare 계정 없이 합성자료를 시연**할 수 있도록 별도 `v2/gemini-direct.js`와 AI 연결 방식 선택 UI를 추가했습니다. 기존 보안 프록시 경로는 변경하지 않았습니다.

### 실제 화면에서 시험하는 순서

1. [PC 출장결과보고서](https://smile7962.github.io/paju-giljabi/v2/report.html)를 열고 `Ctrl+F5`로 새로고침합니다. 출장계획은 기존과 같이 PC 브라우저에 확정돼 있어야 합니다.
2. 오른쪽 **문장 초안·담당자 확인**에서 **AI 연결 방식 선택 → Gemini API 직접 연결(합성자료 시연 전용)**을 선택합니다.
3. 모델은 기본 `gemini-3.5-flash-lite` 또는 고성능 `gemini-3.8-flash`을 선택합니다. 기존 계정에서는 `gemini-2.5-flash`도 선택할 수 있지만 신규 계정에서 접근이 제한될 수 있습니다.
4. **Gemini API 키**에 Google AI Studio에서 발급한 **별도 시연용 키**를 직접 입력합니다. 키를 GitHub·ChatGPT 채팅·주소창에 공유하지 않습니다.
5. **합성자료로 AI 연결 테스트**를 클릭합니다. 이 버튼은 현재 실제 출장 내용과 무관한 `TripDraft.syntheticSample()` 가상 목적/주소/메모/조치만 전송하고 보고서에는 반영하지 않습니다.
6. 성공하면 **실제 업무 메모 대신 직접 만든 가상 목적·현장확인·조치사항**을 보고서 입력창에 작성합니다. 직접 연결 모드는 장소·시간·참석자도 가상값으로 강제 대체해서 Gemini로 전달합니다.
7. 전체 작성내용이 합성자료임을 확인한 뒤 체크박스를 체크하고 **생성형 AI 초안 요청**을 누릅니다. 확인창에서 재확인한 뒤 초안만 미리보기에 표시합니다.
8. 문장 중 사실 추가나 부정확한 표현을 수동 수정하고 **확인 후 적용**을 눌러야 보고서에 반영됩니다. 원본 HWPX로 저장할 때에도 기존 사용자 확인·원본 서식을 유지합니다.
9. 시연을 마치면 **입력된 API 키 지우기** 버튼을 누르고 탭을 닫으세요. 모드를 프록시로 바꾸거나 탭을 종료해도 입력값을 제거합니다.

### 두 연결 방식과 보안

| 모드 | API 키 관리 | 사용 범위 |
|---|---|---|
| **직접 연결** | 브라우저 비밀번호 입력창에 일시 보관, 서버·GitHub·localStorage·URL에 저장 안 함 | **합성자료 시연 전용** |
| **보안 프록시** | 서버측 `GEMINI_API_KEY` 비밀변수 및 별도 접근 토큰 | 기관 승인을 받은 환경에서만 실제 자료 사용 가능 |

- **중요:** 직접 연결에서 API 키는 웹페이지의 JavaScript/브라우저 개발자 도구/확장프로그램으로 접근 가능합니다. 입력창이 비밀번호 형태라는 것만으로 키가 안전하게 보호되는 것은 아닙니다. Google은 운영용 클라이언트 노출을 금지하도록 권장합니다. 가능하면 **시연 전용 새 키**를 사용하고 Google AI Studio에서 Gemini API 전용으로 제한하세요.
- 사용자는 AI 생성 버튼을 누르기 전에 목적·확인·조치의 모든 내용에 실제 민원·주소·이름·개인정보가 없음을 확인해야 합니다. **실제 출장지의 주소·시간·참석자는 직접 연결 요청에서 합성값으로 대체**합니다. 단, 텍스트 메모 자체의 개인정보 여부를 자동 탐지하지는 않습니다.
- 직접 연결의 요청 바디에는 `purpose,address,visitTime,attendees,check,action` 여섯 문자열만 포함됩니다. **사진·원본 HWPX·출장ID·다른 방문지 정보는 전송하지 않습니다.**
- API 호출 구조: REST `/v1beta/models/{model}:generateContent`, `x-goog-api-key` 헤더, `generationConfig.responseFormat.text` JSON 스키마. 응답은 세 문자열만 검증·표시합니다.
- 입력 초과·모델 선택 오류·CORS·키 권한·API 사용량 초과는 사용자에게 안내합니다. 브라우저 CORS 정책으로 직접 호출이 차단되면 **보안 프록시 방식으로 전환**해야 합니다.
- 로컬 문장 정리(생성형 AI 아님), 기존 Worker, QR·현장사진·HWPX 저장 엔진은 변경하지 않았습니다.
- 무료 Gemini API 등급 데이터는 Google의 정책에 따라 제품 개선에 사용될 수 있습니다. 시연자료만 사용하세요. 모델별 무료 이용 가능 여부와 요금은 계정에서 확인합니다.
